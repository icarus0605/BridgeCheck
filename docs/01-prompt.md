# 01. 작업 프롬프트

## 1. 이번 회차 작업 지시

BridgeCheck — 웹·앱 연동 변경 영향 점검기의 Prompt → PRD → 컨텍스트를 한국어로 작성하세요. 교차검토 요지와 이전·새 계약 샘플을 포함하고, legacy TXT 두 개는 수정 없이 보존하세요. 이번 회차에는 제품 구현, 하네스, 코드 생성, 제품 내 AI를 완료했다고 쓰지 마세요.

React 웹뷰는 즉시 배포되지만 Android/iOS 구버전은 스토어 업데이트 전까지 남습니다. 최신 웹 × 구버전 앱의 계약 변경 영향만 점검하고, 구버전 웹(앱 내장 번들·캐시)은 제외한다고 화면과 보고서에 명시하도록 요구사항을 작성하세요.

## 2. 후속 구현용 요구사항

- 입력은 이전·새 계약 JSON 두 개이며 legacy B절의 단일 action 계약 형식을 그대로 사용하세요. 평면 필드만 지원하세요.
- 미지 키 처리 설정은 구앱 요청 파서와 신웹 응답 파서 각각 `무시 / 거부 / 미확인(기본)`이라는 동일한 단일 선택 방식만 제공하세요. 플랫폼·버전 추정 설정을 추가하지 마세요.
- [PRD §4](02-prd.md#4-판정-규칙)의 표를 기준으로 변경 목록과 방향별 영향표를 작성하세요. 오류는 장애 확정이 아니라 계약상 비호환 가능성으로 설명하세요.
- 재검수 항목, 테스트 예시, 복사 가능한 보고서를 제공하세요. 최소 앱 버전 게이팅은 대응 선택지로만 제시하고 버전 번호는 추정하지 마세요.
- legacy D·F절을 [PRD §6](02-prd.md#6-입력-검증과-안전-출력)에 맞게 재사용하세요. 이전 시나리오 입력과 플랫폼별 수동 응답 검사는 새 입력 범위로 가져오지 마세요.
- 외부 라이브러리 없는 단일 index.html로 오프라인 실행 가능하게 설계하세요. 제품 내 AI나 외부 API를 실행 필수 조건으로 두지 마세요.
- 사람의 확인 항목과 미검증 범위를 분리하고, 구현·실행·배포 여부를 실제 증거로 기록하세요.

## 3. 산출물과 완료 기준

README, PRD, 컨텍스트, 검토 기록, legacy 원본 두 개, 계약 샘플 두 개를 제공합니다. README에는 심사 기준 네 가지 순서대로 문서 경로와 절 번호를 연결합니다. 샘플 v1은 legacy B절 그대로, v2는 PRD §9의 변경 일곱 건만 포함합니다. `contractVersion`은 추가 변경을 만들지 않도록 유지하며 앱 버전이나 호환성 증거로 해석하지 않습니다.

문서 단계 완료 기준은 요구사항 일치, 링크 유효성, 원문 보존, JSON 유효성 및 일곱 변경의 확인입니다. 후속 제품 검수와 혼동하지 마세요.
