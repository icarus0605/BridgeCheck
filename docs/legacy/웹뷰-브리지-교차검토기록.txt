웹뷰 브리지 점검기 교차 검토 기록 / 2026-10-22

[Claude 1차 검토 원문]
검토 결과입니다. 기획안과 제작 프롬프트 사이에 판정 규칙이 비어 있거나 어긋난 곳이 있어, 아래 항목은 구현 전에 고쳐야 합니다.

1. **callbackId 무효 시 판정 경로가 정의되지 않음.** E는 공백 callbackId를 "거부"한다고만 쓰고, 그것이 전체 중단인 입력 오류인지 공통 요청 오류인지 밝히지 않습니다. 또 "유효한 요청 ID와 정확히 비교"라는 문구는 요청 ID가 무효일 때 응답 callbackId 비교를 어떻게 할지 암시만 합니다. 구현자가 응답 측 callbackId 불일치로 처리하면 플랫폼에 오탐이 생깁니다. 공백 callbackId는 공통 요청 오류, 두 플랫폼의 callbackId 비교는 미검사로 명시하세요.

2. **마스킹이 키 이름까지 지우면 발견 항목이 무의미해짐.** F는 "민감한 키와 그 하위 값을 [MASKED]로 대체"라고 했는데, 계약에 accessToken 같은 필수 필드가 있으면 결과가 "필드 [MASKED] 누락"이 됩니다. 키 이름은 그대로 두고 값만 마스킹하도록 고치세요. 입력 오류 메시지도 같은 정책 적용 대상인지 한 줄로 못 박아야 합니다.

3. **기획안은 범용 도구처럼 읽히는데 프롬프트는 단일 action만 지원.** 한 줄 소개와 "중요한 범위"에 계약당 action 1개 제한이 없어, 심사자는 여러 액션 대조를 기대하게 됩니다. 범위와 심사용 설명에 "계약 1건당 action 1개, 다중 action은 후속"을 추가하세요.

4. **예시 버튼 수가 문서 간에 다름.** MVP 5항은 버튼 4개, G절은 지원선언 누락과 error status 정상 응답까지 6개 사례를 검수 대상으로 둡니다. 두 사례는 JSON 상수 하나씩이라 비용이 거의 없으니 버튼 6개로 통일하거나, 나머지 둘을 README의 수동 검수 항목으로 명시하세요. 지금은 "검수했다"의 기준이 모호합니다.

5. **supportedActions 중복이 전체 검사를 중단시킴.** "고유한 문자열 배열"을 시나리오 구조 조건으로 두면, iOS 선언에 중복 한 줄만 있어도 Android 결과까지 사라집니다. 중복은 해당 플랫폼의 선언 오류로 격하해 다른 플랫폼 검사는 유지하세요.

6. **75분 안에 G절 전체를 실행 검수하기 어려움.** D절의 계약 검증과 F절의 전 채널 마스킹만으로 10~35분 구간을 넘길 가능성이 큽니다. 현재 생략 순서에 "장식, TXT"만 있는데, 다음 순서를 추가로 적어 두세요.
   - 1순위 생략: JSON 입력창 접기 기능.
   - 2순위 축소: G절 체크리스트 중 예시 버튼으로 재현되지 않는 항목은 README에 "미실행"으로 표기하고 넘어감.
   이렇게 적어야 "미검증을 검증완료로 쓰지 말라"는 요구와 시간 배분이 충돌하지 않습니다.

판정 오탐 관점에서 그 외 규칙은 일관됩니다. 선택 필드의 null을 오류로 보는 것, 두 플랫폼 값을 서로 비교하지 않는 것, 미검사를 통과로 합산하지 않는 것은 모두 의도대로 명시되어 있습니다. 업무 가치 설명도 미측정이라고 밝혀 과장이 없습니다.

위 여섯 항목 외 추가 수정사항은 없습니다.
