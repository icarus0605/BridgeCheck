웹뷰 브리지 점검기 — BridgeCheck
기획안 및 제작 프롬프트 / 2026-10-22

[1. 기획안]

한 줄 소개
React 웹뷰와 Android·iOS 사이의 메시지 약속을 수동 예시로 대조하고,
어느 방향에서 어떤 규격이 어긋났는지 근거와 함께 보여주는 오프라인 도구.
계약 한 건당 action 하나를 점검하며, 여러 action 일괄 검사는 후속 범위.

사용자와 문제
- React 웹뷰 개발자, Android/iOS 앱 개발자, 연동 QA 담당자.
- 액션명, 필수 파라미터, 응답 이벤트명, 콜백 식별자가 다르면 연동 확인이 길어진다.
- 공통 규격과 플랫폼별 예시를 한 화면에서 비교하고 전달용 점검표를 만든다.

중요한 범위
- 이 도구는 팀이 입력한 계약과 메시지 예시를 점검한다.
- 앱 실행, 실제 핸들러 등록, 콜백 도착, 타임아웃, 권한, 스레드, OS 동작은 확인하지 않는다.
- supportedActions도 사람이 입력한 선언 목록이며 실제 앱에서 추출한 정보가 아니다.
- Android/iOS 비교는 각 예시를 같은 계약에 대조하는 것이다.
  두 플랫폼의 photoId 같은 값이 다르다고 오류로 처리하지 않는다.
- 이 메시지 형식은 교육용 팀 자체 규약이며 React/Android/iOS 공통 표준이 아니다.

75분 MVP
1) 계약 JSON 입력창과 시나리오 JSON 입력창.
2) React 요청 공통 점검, Android/iOS 수동 선언 및 응답 점검.
3) 플랫폼별 결과표: 정상 / 오류 / 확인 필요 / 미검사.
4) 고정 양식 점검 보고서 복사. 클립보드 실패 시 직접 선택해 복사.
5) 정상·요청오류·iOS 응답오류·응답미제공·지원선언오류·정상오류응답의 예시 버튼 6개.
시간이 남으면 TXT 다운로드 추가. 파일 업로드, 그래프, 코드 생성은 후속.

화면
- 상단: 목적, 검사 범위, '실제 앱 실행 검증 아님' 안내.
- 왼쪽: 계약 및 시나리오 JSON, 예시 선택, 점검/초기화.
- 오른쪽: 공통 요청 결과와 Android/iOS 결과 카드.
- 하단: 근거 표와 복사할 점검 보고서.

검사할 항목
- 요청 action이 계약 action과 같은가.
- 요청 payload의 필수 필드·자료형·허용값이 계약과 맞는가.
- 각 플랫폼의 supportedActions에 계약 action이 선언되어 있는가.
- 응답 event가 계약 responseEvent와 같은가.
- 응답 callbackId가 요청 callbackId와 정확히 같은가.
- status가 success/error인가. 상태별 payload 필수 필드와 자료형이 맞는가.
- 응답이 없으면 '응답 미제공: 확인 필요'. 시간 초과라고 추정하지 않는다.

시연 구성(약 60초)
1) 정상: 두 플랫폼 모두 '제공 예시 기준 계약 점검 통과'.
2) 요청오류: quality 누락 → 공통 React 요청 오류.
3) iOS 응답오류: event 오타 및 callbackId 불일치 → Android 통과, iOS 오류.
4) 누락 수정 후 재점검 → 오류 제거.
사람의 판단: 실제 앱에서 핸들러/권한/콜백 동작을 확인하고 최종 승인.

75분 배분(목표이며 완료 보장 아님)
- 0~10분: 계약과 예시, 기본 화면.
- 10~35분: 입력 검증과 검사 엔진.
- 35~50분: 결과표, 보고서, 예시 버튼.
- 50~75분: 아래 검수와 오프라인 실행 확인, 시연 준비.
- 시간이 부족하면 장식/TXT 다운로드, 이어서 입력창 접기를 생략.
- 예시 버튼 6종과 오프라인 실행/출력 안전성은 우선 검수. 추가 경계 사례를 실행하지 못하면
  README에 미실행으로 남기며 검증 완료로 표시하지 않음. 전체 구현/검수 완료를 보장하지 않음.

심사용 설명
문제: 웹과 앱이 각자 구현한 브리지 규격 차이를 수동으로 찾는 반복 작업.
해결: action 하나의 계약으로 React 요청과 두 플랫폼 예시를 검사해 불일치 위치를 제시.
효과: 반복 대조와 문의 정리에 쓰는 시간을 줄이는 것이 목표. 실제 절감 수치는 미측정.
개발 과정: PRD, 제작 프롬프트, 실제 교차 검토 기록을 제시.
판단 경계: 도구는 규격 위반을 찾고, 실제 앱 동작과 계약 변경 여부는 사람이 판단.

[2. 제작 프롬프트 — 아래부터 복사]

BridgeCheck라는 웹뷰 브리지 계약 점검기를 구현해 주세요.
아래 명세만 구현하고 추가 기능으로 범위를 확대하지 마세요.
완성품은 AI와 네트워크 없이 작동해야 합니다.

A. 실행 조건
- 단일 index.html 안에 CSS와 일반 JavaScript를 포함합니다.
- file://로 직접 실행합니다. 설치, 빌드, 서버, ES module, fetch, CDN,
  외부 폰트/라이브러리/API/분석 도구/외부 링크 자동 요청을 사용하지 않습니다.
- 모든 처리는 브라우저 메모리에서 수행합니다. 자동 저장, 쿠키,
  localStorage, IndexedDB, Service Worker를 사용하지 않습니다.
- 사용자 입력은 코드로 실행하지 않습니다. DOM 출력은 textContent 또는 value를 사용합니다.
- 한국어 UI. 계약과 시나리오 두 입력창, 점검·초기화·예시·보고서 복사 버튼.
- JSON 원본 입력창에는 원문이 남는다는 안내를 둡니다. 접기는 시간이 남으면 추가합니다.

B. 팀 자체 메시지 계약
단일 action만 지원합니다. 아래는 예시이며 네이티브 표준이라고 표시하지 마세요.
{
  "contractVersion": "1.0",
  "action": "openCamera",
  "responseEvent": "cameraResult",
  "requestFields": [
    {"name":"quality","type":"string","required":true,"enum":["low","high"]},
    {"name":"saveToAlbum","type":"boolean","required":false}
  ],
  "successFields": [
    {"name":"photoId","type":"string","required":true}
  ],
  "errorFields": [
    {"name":"code","type":"string","required":true},
    {"name":"message","type":"string","required":true}
  ]
}

C. 시나리오 입력
{
  "webRequest": {
    "action":"openCamera",
    "callbackId":"cam-001",
    "payload":{"quality":"high","saveToAlbum":false}
  },
  "android": {
    "supportedActions":["openCamera"],
    "response":{
      "event":"cameraResult","callbackId":"cam-001","status":"success",
      "payload":{"photoId":"android-example-001"}
    }
  },
  "ios": {
    "supportedActions":["openCamera"],
    "response":{
      "event":"cameraResult","callbackId":"cam-001","status":"success",
      "payload":{"photoId":"ios-example-002"}
    }
  }
}

D. 입력 검증과 필드 규칙
- 계약/시나리오 각각 1,048,576 UTF-8바이트까지 허용. 초과 시 파싱 전에 거부.
- BOM 제거와 JSON 전체 trim만 수행. 필드 값은 자동 보정하거나 trim하지 않음.
- 최상위는 object이며 null/array는 불가. 필수 구조 검증.
- 파싱 실패 시 입력명과 고정 안내만 표시. error.message와 원문 조각 표시 금지.
- contractVersion/action/responseEvent는 공백만 있지 않은 문자열.
- requestFields/successFields/errorFields는 배열. 빈 배열은 명시적으로 제약 없음으로 처리.
- 각 규칙은 name/type 필수. type은 string/number/boolean/object/array만 지원.
- required 생략 시 false, 지정 시 boolean. name은 비공백 문자열이며 같은 배열에서 중복 금지.
- name에 점이나 대괄호가 포함되거나 __proto__/prototype/constructor와 같으면 미지원으로 거부.
- enum은 string/number/boolean 규칙만 지원. 같은 type의 비어 있지 않은 배열만 허용.
- 미지원 규칙 속성(nullable/maxLength 등)은 무시하지 말고 해당 속성을 안내하며 거부.
- payload 직속 필드만 검사. 재귀 스키마/배열 요소/경로 해석 미지원.
- own-property만 참조. 필수 키 부재는 오류, 선택 키 부재는 검사 대상 밖.
- 존재하는 null은 오류. 0/false는 누락이 아님.
- 필수 string의 빈 문자열은 오류. 선택 string의 빈 문자열과 공백 문자열은 허용.
- 자료형 자동 변환 없음. object는 null/array 제외. array는 Array.isArray로 판정.
- 자료형 불일치 시 해당 필드의 enum 검사 중단. enum은 엄격 일치.
- 미정의 payload 키는 정보만 표시하며 오류로 판정하지 않음.
- JSON.parse의 중복 키 덮어쓰기와 큰 정수 정밀도 한계를 README에 기록.

E. 검사 흐름과 판정
- 계약 또는 시나리오의 구조가 잘못되면 전체 검사를 중단하고 '입력 오류'를 표시.
- webRequest에는 action/callbackId 문자열과 object payload가 필수.
- 요청 callbackId가 빈 문자열/공백만 있는 문자열이면 공통 요청 오류. 전체 구조 오류로 중단하지 않음.
  이때 두 플랫폼 응답의 callbackId 상관 비교는 미검사로 두며 불일치 오류를 만들지 않음.
  callbackId 값은 임의 변환하지 않음.
- action 불일치는 공통 요청 오류. 잘못된 액션에 계약 payload 규칙을 적용하지 말고 미검사 표시.
- action 일치 시 requestFields 검사. 필수값 누락 등은 공통 요청 오류로 묶음.
- android/ios에는 supportedActions 배열과 response 키가 필수.
- supportedActions는 비어 있어도 되는 비공백 문자열 배열.
  중복 항목은 해당 플랫폼의 지원 선언 오류로 표시하고 다른 플랫폼 및 독립 검사는 유지.
  계약 action이 없으면 '수동 지원 선언 불일치' 오류. 실제 핸들러 부재라고 단정 금지.
- response는 null 또는 object. null이면 '응답 미제공: 확인 필요'.
- response object에는 event/callbackId/status 문자열과 object payload가 필수.
- event는 responseEvent와 정확히 비교. callbackId는 유효한 요청 ID와 정확히 비교.
- status는 success 또는 error만. 그 외는 오류로 표시하고 상태별 payload 검사는 미검사.
- success는 successFields, error는 errorFields로 검사.
- 유효한 error 응답의 형식이 맞으면 '오류 응답 형식 점검 통과 / 기능 성공 여부 별도'로 표시.
- 공통 요청 오류가 있으면 두 플랫폼의 최종 판정은 통과 금지.
  독립적으로 확인 가능한 플랫폼 선언/응답 항목은 검사하되 각 결과를 구분.
- 판정 우선순위: 확인된 오류가 있으면 오류, 없고 미제공이 있으면 확인 필요,
  전부 검사해 통과하면 '제공 예시 기준 계약 점검 통과'. 미검사를 정상으로 합산하지 않음.
- 결과에 검사 항목/플랫폼/필드 위치/기대 조건/실제값/판정 근거를 표시.
- 실제값을 두 플랫폼끼리 단순 동등 비교하지 않음. 플랫폼별 차이를 버그로 단정하지 않음.
- 실제 앱 접근·콜백 실행·자동 수집·타임아웃 진단은 구현하지 않음.

F. 원문 노출 방지와 보고서
- password/token/authorization/secret/apiKey를 대소문자 무시 부분일치로 찾고,
  민감 키의 값과 하위 값 전체를 결과와 보고서에서 [MASKED]로 대체.
  필드명/경로는 유지해 누락 위치를 알 수 있게 함. 값 마스킹 정책은 입력 검증 안내에도 적용.
  원문 파싱 오류는 고정 안내만 표시하며 필드 값이나 네이티브 오류 문자열을 노출하지 않음.
- 기대값/실제값/추가필드 정보 등 모든 결과 채널에 같은 정책을 적용.
- object/array 실제값은 내용 대신 타입과 개수만 표시.
- 문자열은 마스킹 후 최대100코드포인트만 표시하고 생략 여부 표시.
- 값 패턴으로 모든 개인정보를 탐지하지 않는다는 안내와 공유 전 검토 안내.
- 보고서는 계약 버전/action, 공통 요청 결과, 플랫폼별 결과, 발견 항목,
  사람이 실제 앱에서 확인할 항목으로 고정 구성. 원본 JSON 전체 포함 금지.
- 복사 실패 시 읽기전용 textarea에서 직접 선택/복사 가능하게 함.
- 초기화는 입력/결과/보고서를 지우고 예시를 자동 재입력하지 않음.
- TXT 다운로드는 시간 남을 때만 추가. 추가하면 고정 안전 파일명과 Blob URL 해제.

G. 예시 버튼 6개와 검수
- 정상: photoId 값은 플랫폼마다 달라도 둘 다 통과.
- 요청오류: quality 누락을 공통 오류로 검출하고 플랫폼 최종 통과 금지.
- iOS 응답오류: event 오타와 callbackId 불일치 각각 검출.
- 응답미제공: null을 타임아웃으로 단정하지 않고 확인 필요.
- 지원선언오류: iOS supportedActions에 계약 action이 없으면 수동 지원 선언 불일치 검출.
- 정상오류응답: error status의 유효한 오류 응답에 성공 payload 규칙을 적용하지 않음.
- 0/false, null, 빈 문자열, 자료형 오류, 미등록status, 잘못된JSON/명세,
  unsupported rule, 추가필드, 마스킹, XSS문자열, 초기화를 확인.
- 비공백 요청 callbackId와 플랫폼별 중복 선언의 오류 분리도 검수.
- 시간이 부족하면 예시 6종/오프라인 실행/마스킹과 XSS 출력/초기화를 우선 검수하고,
  나머지 경계 사례는 실행 여부를 개별 기록. 미실행 항목이 있으면 전체 검증완료라고 쓰지 않음.
- 브라우저에서 file:// 실행과 복사 대체 경로를 확인.
- 외부 네트워크 요청이 없는지 관찰하고, 네트워크를 끊어도 핵심 기능이 동작하는지 별도 확인.
